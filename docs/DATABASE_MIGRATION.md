# DATABASE_MIGRATION.md — نقل قاعدة بيانات FekrahEdu إلى PostgreSQL على سيرفر خاص

> هذا المستند **تحضيري فقط**. لم يُنفَّذ أي Migration حقيقي، ولم يتغيّر DNS ولا الدومين ولا بيانات الإنتاج.
> الموقع الحالي يعمل كما هو على البنية الحالية.

---

## 1. الوضع الحالي بعد إعادة الهيكلة

### طبقة البيانات (Frontend)

لا يوجد أي استعلام قاعدة بيانات داخل الصفحات أو المكوّنات. كل شيء يمر عبر:

```
src/data/
├── index.ts                     ← نقطة الاستيراد الوحيدة للتطبيق
├── config.ts                    ← يقرأ إعدادات الاتصال من Environment Variables فقط
├── types.ts                     ← عقود مستقلة (DataBackend, Filter, Row, ...)
├── dataClient.ts                ← db + activeDataDriver (اختيار المزوّد وقت التشغيل)
├── drivers/
│   ├── lovableCloudDriver.ts    ← المزوّد الحالي (الافتراضي)
│   └── selfHostedDriver.ts      ← مزوّد REST للسيرفر الخاص (جاهز، غير مفعّل)
├── auth/
│   ├── types.ts                 ← عقد AuthProvider مستقل
│   ├── cloudAuthProvider.ts     ← المصادقة الحالية
│   ├── selfHostedAuthProvider.ts← مصادقة السيرفر الخاص (جاهزة، غير مفعّلة)
│   └── authService.ts           ← الخدمة الموحّدة التي تستخدمها الواجهة
├── repositories/                ← مستودعات لكل كيان (عملاء، طلبات، فواتير، تمويل، تذاكر...)
└── legacy/client.ts             ← وصلة انتقالية تُبقي الشاشات القديمة تعمل بلا تغيير سلوكي
```

### طبقة الخادم (جاهزة للنقل، غير مشغّلة)

```
server/
├── src/index.ts                 ← نقطة تشغيل الـAPI
├── src/env.ts                   ← كل الإعدادات من متغيرات البيئة
├── src/db/pool.ts               ← اتصال PostgreSQL + withUser لتفعيل RLS
├── src/db/queryBuilder.ts       ← بناء الاستعلامات بقائمة سماح للأسماء (حماية من الحقن)
├── src/config/tables.ts         ← قواعد الوصول لكل جدول + الدوال المسموح استدعاؤها
├── src/routes/                  ← data / auth / rpc / functions / realtime
├── scripts/migrate.mjs          ← مشغّل ملفات الترحيل
└── migrations/                  ← مخطط قاعدة البيانات الحالي كاملاً
```

## 2. ملفات الترحيل الجاهزة

مستخرجة من قاعدة البيانات الحالية (مخطط فقط، بدون بيانات):

| الملف | المحتوى |
|---|---|
| `0001_extensions.sql` | الإضافات (pgcrypto, uuid-ossp, pg_trgm...) |
| `0002_types.sql` | الأنواع و الـEnums |
| `0003_tables.sql` | كل الجداول والأعمدة والقيم الافتراضية |
| `0004_functions.sql` | الدوال المخزّنة |
| `0005_constraints.sql` | المفاتيح الأساسية والأجنبية وUnique وCheck |
| `0006_indexes.sql` | الفهارس |
| `0007_triggers.sql` | المحفزات |
| `0008_rls_policies_supabase.sql` | سياسات RLS كما هي حاليًا (تحتاج تكييفًا — انظر §5) |
| `0010_replica_identity.sql` | إعدادات المزامنة اللحظية |

التوثيق الكامل للمخطط (جداول، أعمدة، أنواع، مفاتيح، علاقات، فهارس، قيود) في **`docs/DATABASE_SCHEMA.md`**.

## 3. خطوات النقل عند اتخاذ القرار

1. **تجهيز السيرفر**: PostgreSQL 15+، ونسخ احتياطي مجدول.
2. **إنشاء المخطط**:
   ```bash
   cd server && cp .env.example .env   # املأ بيانات الاتصال
   node scripts/migrate.mjs
   ```
3. **نقل البيانات**: تصدير من البيئة الحالية بـ `pg_dump --data-only` واستيراده بعد إنشاء المخطط. يُنفَّذ بترتيب المفاتيح الأجنبية.
4. **نقل المستخدمين** (انظر §4).
5. **تشغيل الـAPI**: `npm install && npm run start` داخل `server/`، خلف HTTPS.
6. **تبديل الواجهة**: تغيير متغيرات البيئة فقط، بدون تعديل كود:
   ```
   VITE_DATA_DRIVER=self-hosted
   VITE_AUTH_DRIVER=self-hosted
   VITE_API_BASE_URL=https://api.fekrahedu.com
   ```
7. **اختبار على بيئة تجريبية أولًا**، ثم التحويل النهائي.

---

## 4. المصادقة (أهم نقطة)

المستخدمون حاليًا في مخطط المصادقة المُدار، وهو **غير مشمول** في ملفات الترحيل. عند النقل:

1. إنشاء جدول `app_users` (موجود في كود الخادم، يحتاج ملف ترحيل عند التنفيذ):
   `id uuid PK`, `email citext unique`, `password_hash text`, `raw_user_meta_data jsonb`, `email_confirmed_at`, `created_at`.
2. تصدير المستخدمين مع **معرّفاتهم الحالية (id)** — إلزامي، لأن كل الجداول تربط بها.
3. **كلمات المرور**: المخزّن هو bcrypt. إن أمكن تصديره تُنقل الحسابات بلا إزعاج للمستخدمين. إن تعذّر → حملة إعادة تعيين كلمة مرور إجبارية قبل التحويل.
4. جدول `user_roles` ينتقل كما هو — صلاحيات الأدمن محفوظة.
5. تسجيل الدخول بجوجل يحتاج إعادة تسجيل تطبيق OAuth باسم نطاق الـAPI الجديد.

---

## 5. RLS على السيرفر الخاص

السياسات الحالية تعتمد على `auth.uid()`. على السيرفر الخاص:

- الخادم يضبط هوية المستخدم لكل طلب عبر `set_config('app.user_id', ...)`.
- يجب استبدال `auth.uid()` بدالة محلية تقرأ هذا الإعداد، وإنشاء دور قاعدة بيانات محدود الصلاحيات للتطبيق.
- لذلك `0008_rls_policies_supabase.sql` يُطبّق **بعد** هذا التكييف، لا قبله.

---

## 6. ما زال مرتبطًا بالبيئة الحالية

| العنصر | الحالة |
|---|---|
| المصادقة وكلمات المرور | تحتاج نقلًا يدويًا (§4) |
| الدوال السحابية (Edge Functions) — واتساب، بريد، دفع، ذكاء اصطناعي | تحتاج إعادة نشر كخدمات على الخادم (`server/src/routes/functions.ts` جاهز لاستقبالها) |
| تخزين الملفات والمرفقات | يحتاج مخزّنًا متوافقًا مع S3 أو قرصًا على السيرفر |
| المزامنة اللحظية | الخادم يدعمها عبر SSE + `pg_notify`؛ تحتاج محفزات إشعار على الجداول المعنية |
| البريد الصادر `notify.fekrahedu.com` | مرتبط بالبنية الحالية، يحتاج إعادة ربط |

## 7. الجاهز للنقل الآن

- المخطط الكامل + التوثيق + ملفات الترحيل.
- كل استعلامات الواجهة عبر طبقة واحدة قابلة للتبديل بمتغير بيئة.
- طبقة مصادقة مجرّدة، والواجهة لا تعرف المزوّد.
- هيكل API كامل بقواعد وصول وقائمة سماح للجداول والدوال.

## 8. مخاطر يجب معالجتها قبل النقل الفعلي

1. **كلمات المرور** — أكبر خطر؛ يُحسم قبل أي جدولة.
2. **RLS** — تطبيق السياسات بلا تكييف قد يحجب البيانات أو يكشفها. تُختبر كل سياسة على بيئة تجريبية.
3. **الدوال السحابية** — إن لم تُعَد قبل التحويل، تتوقف إشعارات واتساب والبريد والدفع.
4. **المرفقات** — روابط الملفات القديمة يجب أن تبقى صالحة أو يُعاد توليدها.
5. **فترة التوقف** — تُحدَّد نافذة صيانة؛ الكتابة توقف أثناء نقل البيانات لتفادي فقد سجلات.
6. **النسخ الاحتياطي والتراجع** — نسخة كاملة + خطة رجوع قبل التحويل.
